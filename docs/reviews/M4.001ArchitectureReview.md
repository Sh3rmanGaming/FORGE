# M4.001 Subject Identity Architecture Review

**Status:** Review
**Date:** 2026-08-22
**Scope:** Architecture and contract design only

## Review Objective

Determine whether the proposed Subject Identity boundary is sufficiently
stable for M4.002 and later gameplay-domain architecture without redefining
frozen M2/M3 identity or persistence.

## Evidence-Based Findings

1. ForgeOS already isolates `player.local` behind its player resolver and states
   that it is not stable multiplayer identity.
2. Communications intentionally persists and validates only `player.local`
   within its accepted M3 scope.
3. Both namespaces are savegame-global and must remain byte/meaning compatible.
4. No accepted stable multiplayer principal source currently exists.
5. Future gameplay domains need stable ownership references before their
   persisted schemas are designed.
6. A new additive identity namespace and one-way compatibility resolver satisfy
   that dependency without rekeying frozen state.

## Proposed Decisions

| Decision | Proposed M4.001 contract | Reason |
|---|---|---|
| Identity scope | Stable within one authoritative save lineage | Matches FORGE persistence authority without claiming cross-save accounts |
| Subject categories | `player`, `organisation`, `system` | Covers future owners and actors while keeping their domain rules separate |
| Subject ID form | `subject.<category>.<authority-owned-key>` | Makes category explicit and prevents collision with external definition IDs |
| Generated keys | Server-owned positive unpadded decimal sequences per generated category | Deterministic, persistable, and caller-independent |
| Built-in system subject | `subject.system.forge` | Provides one controlled non-player actor without generic caller-selected system IDs |
| Persistent namespace | `forge.identity`, schema version 1 | Keeps identity truth domain-specific and additive |
| Legacy seam | Private one-way `player.local -> subject.player.N` mapping | Preserves M2/M3 storage and supplies future domain identity |
| First bootstrap | Create system subject, first player subject, and legacy binding only when namespace is absent | Supports existing saves without M2/M3 migration |
| Binding authority | Only approved bootstrap/authenticated authority adapters | Prevents client self-assertion |
| Identical bind | Idempotent `success` | Avoids duplicate mutation without inventing an error |
| Organisation allocation | Identity capability exists but remains unavailable to general callers until M6 owner is approved | Avoids implementing company lifecycle in M4 |
| Multiplayer source | Must be proven later by an authenticated authority adapter | Avoids inventing an unstable FS25 account identifier |
| Public exposure | None during M4.001 | M4.005 must settle API/version ownership first |

## Layer and Ownership Review

```text
authenticated/local-authority adapter
            |
            v
private principal/legacy binding port
            |
            v
Subject Identity Service ---- owns IDs, immutable type, bindings
            |
            v
forge.identity persistence

Future domains store subjectId references only.
ForgeOS and Communications continue storing player.local.
```

The proposed service does not become a generic profile, permission, company,
account, or progression manager.

## Compatibility Assessment

### Remains valid unchanged

- `FORGE.Definitions.ForgeOSPlayerId.LOCAL`;
- `forge.os` player maps and schema;
- `forge.communications` player maps, recipient rules, and schema;
- savegame-global M2/M3 persistence;
- ForgeOS and Communications domain ownership; and
- Phone/Laptop presentation behavior.

### Additive seam

- new `forge.identity` namespace;
- new internal subject definitions and Identity diagnostic source;
- private one-way legacy binding; and
- internal ports later consumed by M4.002 and future domain managers.

### Explicitly forbidden reinterpretation

- treating `player.local` as authenticated/global identity;
- renaming old player-map keys to subject IDs;
- copying subject IDs into frozen M2/M3 records;
- deriving subject ID from a display name, client connection order, or device;
  and
- treating save-lineage subject identity as a cross-save platform account.

## Persistence Review

The proposed schema is intentionally version 1 and additive. Before M4.004:

- absent state may bootstrap exactly once;
- valid version 1 may restore;
- malformed/conflicting/future state fails closed through a controlled result;
- identity is not silently regenerated; and
- failed allocation consumes no sequence.

This restricted policy prevents M4.001 from prematurely implementing the common
migration framework owned by M4.004.

## Authority and Privacy Review

- Subject allocation and binding are server/authority-owned.
- Principal evidence is adapter-private and cannot arrive in mutable request
  parameters.
- Raw principal keys are excluded from ordinary queries and diagnostics.
- M4.001 resolves identity but does not grant permission.
- M4.002 will bind the resolved actor into authoritative mutation requests.
- Multiplayer identity remains unverified until a stable authenticated FS25
  principal source passes runtime review.

## Event Policy

M4.001 introduces no public Event Bus contract. Identity creation and binding
are queried through the internal service ports. Any future identity event must
wait for the M4.007 publication/re-entrancy policy or receive a separate
architecture approval.

This avoids defining event semantics out of dependency order.

## Verification Gate Proposed After Implementation Approval

Required evidence:

1. component definitions and validation pass;
2. allocation, lookup, binding, detachment, idempotence, and failure tests pass;
3. absent-state bootstrap is atomic and occurs once;
4. an accepted M3 save retains unchanged ForgeOS/Communications behavior;
5. save, complete FS25 shutdown, new process, and reload restore the identical
   player subject and legacy binding;
6. sequence continuation cannot collide;
7. future/malformed/conflicting identity state does not regenerate identities;
8. the complete retained M1-M3 suite passes;
9. authoritative/generated synchronization and package validation pass; and
10. no multiplayer-complete or gameplay-domain claim is made.

## Risks

- A save-lineage subject is intentionally not a global platform account;
  presenting it as one later would be a contract defect.
- Silent identity regeneration would orphan future domain references and is
  therefore forbidden even when repair appears convenient.
- Persisting raw external principal keys may have privacy/platform constraints;
  the authenticated adapter must define a safe controlled representation before
  multiplayer binding is implemented.
- Source ordering is lifecycle-sensitive: identity must restore before future
  subject-owned domain state, without reordering frozen M2/M3 behavior
  opportunistically.
- Organisation allocation must not become an unowned public operation before
  M6 defines creation authority.

## Approval Questions

The Project Director and Chief Architect should explicitly confirm:

1. subject IDs are stable within one save lineage, not cross-save accounts;
2. initial types are exactly player, organisation, and system;
3. generated player/organisation IDs use authority-owned per-type sequences;
4. `subject.system.forge` is the only M4.001 built-in system subject;
5. `forge.identity` schema version 1 and absent-state bootstrap are approved;
6. `player.local` maps one-way through a private compatibility resolver and old
   namespaces remain unchanged;
7. identical bindings are idempotent success and conflicting bindings fail;
8. raw principal binding data remains private and multiplayer binding waits for
   a proven authenticated principal source;
9. organisation identity allocation remains inaccessible to general callers
   until M6 defines its owner; and
10. M4.001 exposes no public addon API or public identity events.

## Review Outcome

The M4.001 architecture package is complete at Review status. If approved, it
authorizes only the bounded M4.001 definitions, service, persistence,
integration, tests, and runtime-verification work described above. It does not
authorize M4.002, multiplayer transport, gameplay domains, or changes to frozen
M2/M3 schemas.
