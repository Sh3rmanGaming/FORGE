## Cross-Mod Acquisition Proof

In both cycles, production ForgeOS opened registration and subscribed the
export bridge before the companion ran. Cycle 1 line 1558 and Cycle 2 line 1555
prove all of the following in one dependent mod:

- the FORGE dependency was known and loaded;
- `g_messageCenter` was available;
- the custom string topic published successfully;
- exactly one provider responded;
- caller-owned response mutation was visible synchronously;
- bridge protocol version 1 was returned;
- the ForgeOS facade crossed the custom-environment boundary as a table;
- App API version 1 and `supportsAppApiVersion(1)` succeeded;
- the phase remained `registrationOpen`; and
- `registerApp()` returned `success`.

Production froze registration and reached runtime-active only later (Cycle 1
lines 1867-1868; Cycle 2 lines 1864-1865). This proves the required registration
window ordering. The companion used no ClassUtil, ModManager environment
internals, global scan, fallback, or retry.

## Scope and Limitations

This verification proves local client-process MessageCenter transport,
synchronous reference mutation, facade acquisition, registration timing,
Phone visibility and repeatable open/close behaviour, navigation resume, and
SAVEGAME notification restoration. It does not verify dedicated-server use,
multiplayer registration determinism, remote access, RPC, or configurable input
binding UI. Dedicated-server behaviour remains explicitly unverified.

## Conclusion

The version-1 `FORGE.ForgeOSExportBridge` protocol and the M2.010 companion
integration pattern are runtime proven against one traceable two-cycle package
pair. `verification/FS25_FORGE_M2010_Verifier/` is therefore a verified
reference companion implementation. M2.010 runtime verification is complete.
The Project Director and Chief Architect subsequently accepted M2.010 and
applied its bounded contract freeze on 2026-08-09; overall M2 remains in
progress.
