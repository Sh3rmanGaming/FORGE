# FORGE M2.013 Final Architecture Review

**Status:** Accepted

**Milestone:** M2.013 - ForgeOS Polish

## Purpose

This record inventories the implemented ForgeOS Foundation contract for final
M2 review. It distinguishes addon-facing APIs, the cross-mod acquisition
contract, Engine/platform adapters, internal implementation, and intentionally
deferred architecture. Final verification and M2 acceptance remain pending.

## Contract Inventory

### Addon-facing ForgeOS façade

External addons acquire `FORGE.ForgeOS` through bridge version 1 and may use:

- compatibility and phase queries: `getPhase()`, `getAppApiVersion()`,
  `supportsAppApiVersion()`, `isAvailable()`, `isRegistrationOpen()`, and
  `isRuntimeActive()`;
- Device registration and detached queries: `registerDevice()`,
  `isDeviceRegistered()`, `getDeviceDefinition()`, and
  `getRegisteredDeviceIds()`;
- Device visibility: `showDevice()`, `hideDevice()`, and
  `getDeviceVisibility()`;
- application registration and detached queries: `registerApp()`,
  `isAppRegistered()`, `getAppDefinition()`, and `getRegisteredAppIds()`;
- presentation resolution: `resolvePresentation()`;
- lifecycle: `openApp()`, `activateApp()`, `backgroundApp()`, `closeApp()`,
  `getAppLifecycleState()`, and `getActiveAppId()`;
- navigation: `navigate()`, `goBack()`, `getCurrentRoute()`, and
  `getNavigationHistory()`; and
- notifications: `createNotification()`, `markNotificationRead()`,
  `dismissNotification()`, `getNotification()`, and `getNotifications()`.

State-changing operations use the frozen result contracts. Primitive query
semantics, detachment, phase gates, validation precedence, event ordering, and
persistence compatibility remain governed by their accepted milestone records.

### Cross-mod acquisition

The local-process `g_messageCenter` bridge version 1 and topic
`forge.crossMod.forgeOS.request.v1` expose only `FORGE.ForgeOS`. The bridge does
not serialize references or expose FORGE internals.

### Engine/platform adapter contracts

The following methods are owned by Engine/platform integration and are not
addon-facing application APIs:

- `updateRuntimeHost()`;
- `drawRuntimeHost()`;
- `dispatchHostInput()`;
- `dispatchHostPointer()`; and
- `hasVisibleRuntimeHost()`.

`start()`, `completeStartup()`, and `shutdown()` are production lifecycle
orchestration contracts owned by Engine/bootstrap integration. Addons do not
control the ForgeOS lifecycle.

### Internal implementation

Registries, services, State Store, Save Manager, the private runtime Host map,
Host factories, Bootstrap, Registration Coordinator, and executable definition
assets remain internal. Their accepted invariants are frozen where recorded,
but their representation is not an addon API.

## M2.013 Code and Performance Review

- Hidden Hosts do not draw and receive no pointer interaction.
- Host processing order remains the deterministic Phone-then-Laptop sequence.
- Launcher and notification data are obtained through detached read-only façade
  queries; neither Host gained registry or State Store access.
- The bounded launchers cap rendered entries and notification trays cap visible
  records, preventing unbounded per-frame rendering work.
- No persistence write, controller execution, network operation, or arbitrary
  callback occurs during Host draw.
- Existing detached-copy allocations remain bounded by the registered app and
  retained notification capacities. No optimization was justified that would
  weaken detachment or deterministic ordering.
- Temporary per-button callback and cursor investigation logs were removed;
  controlled lifecycle, failure, and actionable diagnostics remain.

## Bounded Visual Polish

PhoneHost and LaptopHost retain the existing presentation architecture while
adding a consistent dark layered shell, orange FORGE OS identity, clearer
typographic hierarchy, card-based launcher treatment, active-surface panels,
notification badges, and input footers. No external concept image is packaged
or treated as a production asset.

The original prototype's rounded Phone frame was promoted into the authoritative
`forgeos/assets/phone_frame.dds` location and is now owned and cleaned up by
PhoneHost as a presentation-only overlay. This reuses a repository asset without
restoring the obsolete prototype Phone implementation.

The synchronization manifest now includes approved authoritative ForgeOS DDS
presentation assets alongside Lua source. Generated copies remain derived and
must match the authoritative asset byte-for-byte.

The matching `app_card.dds` prototype asset was also promoted for rounded Phone
launcher cards. The inner Phone surface was aligned to the frame's screen area
to remove the visible transparent seam. These cards remain non-interactive in
M2; application launch interaction and app-owned menu rendering stay deferred.

Runtime inspection then confirmed that the frame asset already contains its
own complete rounded screen fill. PhoneHost therefore renders no redundant
square full-screen panel when that asset is active; the rectangular background
is retained only as the asset-unavailable fallback.

Runtime inspection showed that the original top-edge accent and header crowded
the frame's speaker/notch treatment. The divider is retained below a dedicated
hardware-safe inset, while the FORGE OS header and active-surface block are
padded downward. This preserves the orange hierarchy without crossing the
physical frame detail.

## Deferred and Non-Freeze Scope

The M2 freeze excludes:

- stable multiplayer identity and comprehensive multiplayer runtime behaviour;
- dedicated-server Host/UI behaviour;
- remote/network façade access;
- application or route-controller execution;
- application-owned custom rendering and an icon-registration system;
- Laptop windows, multiple rendered apps, taskbar/window switching, z-order,
  geometry, focus, text entry, drag-and-drop, or persistent desktop state;
- source-to-app unread badge ownership;
- physical Laptop world-object interaction; and
- other open decisions explicitly classified outside the accepted M2 scope.

## Compatibility and Evolution

The final M2 freeze applies to the implemented Foundation contracts. Compatible
additive evolution remains permitted after documentation, testing, API and
persistence compatibility review. Breaking changes require explicit
architecture approval and migration planning where applicable.
